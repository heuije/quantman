# 발주창 넷팅 (Cross-Strategy Order Netting) 설계

**작성:** 조대표 · 2026-07-02
**모듈:** 자동매매 엔진 (`local/localapp/`, 서버 `routers/trading.py`, 웹 트레이딩 탭)
**상태:** 설계 승인 → 구현 계획 대기

---

## 1. 문제 (일반)

**여러 전략을 함께 연동하면, 같은 종목·같은 발주창에서 서로 반대 방향의 주문이 겹칠 수 있다.**
현재는 각 전략의 주문을 독립적으로 즉시 발주하므로, 겹치는 수량만큼 **불필요한 왕복 수수료·
슬리피지**가 발생한다. 실물 순포지션은 그대로인데 "팔고 즉시 되사는(또는 그 반대)" 거래가 나간다.

이는 특정 전략 조합의 문제가 아니라 **구조적 문제**다. 반대 주문이 겹치는 경로는 여럿이다:
- 청산(매도) vs 진입(매수) — 롱 청산과 롱 진입이 겹침
- 진입(매수) vs 진입(매도) — 한 전략 롱 진입, 다른 전략 숏 진입(선물)
- 청산(매도) vs 청산(매수) — 한 전략 롱 청산, 다른 전략 숏 청산
- 선물뿐 아니라 **주식**도(롱 청산 매도 + 롱 진입 매수 = 워시)

**진실원천:** [runner.py `run_close_cycle`](../../local/localapp/runner.py) 이 종가창에서
`liquidate_day_trades`(청산) → `enter_close_candidates`(진입)를 **각각 즉시 발주**하고,
아침 cycle(`_cycle_body` §2 청산 → §3 진입)도 동일하다. 둘 사이·전략 간 상쇄가 전혀 없다.

### 대표 예시 (A/B — 이 요구의 발단, 일반 규칙의 한 사례일 뿐)

- **전략 A** (S&P500 역추종 당일매매): 하락일 → 시가매수·종가매도(롱), 상승일 → 시가매도·
  종가환매(숏). `direction=long_short`, `fill=next_open`, `hold_days=0`.
- **전략 B** (오버나이트 롱): 항상 종가매수 → 익일 시가매도. `fill=close`.

**하락일**엔 두 발주창 모두에서 반대 주문이 겹친다:

| 발주창 | 청산(전략) | 진입(전략) | 결과 |
|---|---|---|---|
| 종가 (15:40) | A 롱 **매도** | B 롱 **매수** | 왕복 낭비 |
| 익일 시가 (08:55) | B 롱 **매도** | A 롱 **매수** | 왕복 낭비 |

상승일엔 동방향(둘 다 매수 또는 매도)이라 순포지션이 실제로 전환(−1↔+1)되므로 두 주문이 정당하다.

## 2. 목표 · 비목표

**목표:** 한 발주창에서 같은 종목의 **반대 방향 주문이 겹치는 수량만큼** 브로커 주문을
내지 않고 원장만 이관해, 왕복 수수료를 제거한다. 하락일 종가·시가 양쪽 모두.

**비목표:**
- 백테스트 엔진의 종가매수→익일시가매도 패리티(별건 — 라이브만 대상).
- 상계증거금 자체의 재설계(넷팅은 *주문*을 줄일 뿐, 증거금 계산은 브로커 소관).
- 동방향 주문 병합(수수료는 계약당이라 병합해도 절감 없음 — 하지 않는다).

## 3. 핵심 규칙 — 종목별 순증분(net signed delta)

전략·청산/진입 구분과 **무관하게**, 한 발주창에서 종목 S에 대한 **모든 발주 의도**를
부호 합산한다(매수 +, 매도 −):

```
net_S = Σ(매수 수량) − Σ(매도 수량)
```

- **브로커로 나가는 실주문 = net_S** (양수면 |net_S| 매수, 음수면 |net_S| 매도, 0이면 무발주).
- **겹쳐 상쇄되는 수량 = `min(Σ매수, Σ매도)`** — 이 수량은 브로커 주문 없이 원장만 이관(§4).

이 한 규칙이 모든 반대 주문 조합(청산-진입·진입-진입·청산-청산)을 자동 처리한다. 상승일처럼
모든 주문이 동방향이면 `min(Σ매수,Σ매도)=0` → 상쇄 없음 → 전량 정상 발주(순포지션 실제 전환).

**절약 수수료** = `min(Σ매수, Σ매도) × 계약당수수료 × 2` (겹친 계약마다 매수·매도 한 쌍씩 회피).

**불변식 — 상쇄 대상이 없으면(min=0) 입력 주문을 그대로 발주한다(no-op).** 이것이 현행 동작
byte-identical 보존을 보장한다(특히 골든 테스트가 있는 아침 cycle). 종목이 하나뿐인 전략이든
여러 전략이 한 종목에 겹치든 동일 규칙 — 겹침이 없으면 아무것도 바뀌지 않는다.

## 4. 장부 이관 (book-transfer) — 전략별 분리 손익

상쇄되는 `min(Σ매수,Σ매도)` 계약은 **브로커 주문 없이** 원장에서만 이동한다. 실물 포지션은 불변.
각 발주 의도(leg)를 **기준가**로 장부 처리하되, 손익은 leg마다 독립적으로 산정한다:

- **청산 leg** (상쇄분): `realized = (기준가 − 진입가) × 수량 × 부호 × 승수`를 해당 전략 명의로
  `trades.jsonl`에 기록, 원장 슬롯 감소(0이면 삭제) — **`netted=true`·수수료 0**.
- **진입 leg** (상쇄분): 해당 전략 명의로 원장 슬롯 생성/증가(진입가=기준가), 진입 기록 —
  **`netted=true`·수수료 0**.
- **잔여**(net_S 만큼)는 진입/청산 의도 중 일부가 실제 브로커로 발주돼 **실제 체결가**로 기록되고,
  겹친 나머지는 기준가로 장부 처리된다. 어느 leg이 실주문(체결가)·어느 leg이 장부(기준가)를
  받는지 배분은 **FIFO로 결정론적 고정**(구현 계획). 이 배분은 잔여 수량의 `(체결가−기준가)`
  차이만큼만 특정 전략 원가에 영향 — 같은 발주창(≈동시 체결)이라 미미하나, 결정론적이라 재현 가능.

**전략·leg 수 무관:** 청산 2건 + 진입 3건이 겹쳐도 각 leg의 손익은 기준가 기준으로 독립 산정되므로
**closer↔opener를 특정 쌍으로 매칭할 필요가 없다**(matching-free). A/B는 이 규칙의 1:1 사례.

**기준가:** 넷팅 시점의 현재가(`_safe_price`, 종가/시가 무렵) — 실제 청산/진입이 썼을 참조가와 동일.

**손익 정합성(정직성):** 예로 하락일 A롱청산+B롱진입 →
A레그 `(기준가−A진입가)` + B레그 `(익일시가−기준가)` = `(익일시가−A진입가)` = 실제 총손익.
**분할된 레그들의 합이 정확히 참값**이므로 분리해도 정직하다. 기준가는 유일한 분할점이며
`netted` 표시로 "실제 체결 아님·기준가 분할"을 명시한다.

## 5. 통합 구조 — "결정 → 넷팅 → 발주" seam

현행은 결정 즉시 발주한다. 결정(주문 의도 산출)과 발주 사이에 넷팅을 끼운다.

```
local/localapp/netting.py            [신규 · 순수 함수 · 브로커/IO 없음]
    net_window(intended_orders) -> NetResult(
        broker_orders,   # 실제 발주할 순증분 주문 (종목별 net_S)
        book_legs,       # 브로커 없이 장부 처리할 leg (netted 청산/진입)
        savings)         # [{symbol, netted_qty, commission_saved_krw}]
    · intended_orders = 청산·진입 구분 없이 이 발주창의 모든 발주 의도 한 리스트
      [{sid, symbol, strategy, side(buy/sell), qty, ref_price, kind(entry/exit),
        entry_price, definition, ...}]
    · 종목별 부호합산 → net_S 만 broker_orders, min(Σ매수,Σ매도)은 book_legs, 절약 계산
    · 겹침 없으면(min=0) 모든 의도를 broker_orders로 그대로 반환 (no-op = 현행 보존)

trader.py
    · liquidate/enter 경로를 '주문 의도 산출' + '발주'로 분리(청산 클램프·게이트는 산출 단계)
    · _apply_book_leg(leg): 원장 이관 + netted 손익/진입 기록 (브로커 미호출)
    · broker_orders 는 기존 _submit_* 로 정상 발주

runner.py
    · run_close_cycle: (청산 의도) + (진입 의도) 합쳐 net_window → book_legs 적용 + broker_orders 발주
    · 아침 cycle 경로: 동일 seam 적용 (no-op 보장으로 무넷팅 시 현행 보존)

order_log.py
    · 주문/거래 레코드에 netted(bool)·commission_saved 필드
    · cycle 요약에 n_netted·commission_saved_krw

gui.py / gui_format.py
    · 주문내역에 넷팅 행 구분 표시 + 절약액

server/app/routers/trading.py (+ models)
    · cycle 요약의 n_netted·commission_saved_krw 수용·저장 (집계만 — 보안 §4)

web (트레이딩 탭)
    · "오늘 넷팅 N건 · 수수료 X원 절약" + 사이클별 상세
```

## 5.5 진입 사이징 기준 — 넷팅의 핵심 정합성

**문제:** 현재 진입 사이징은 발주마다 브로커 `orderable_qty`를 **live로 재조회**하고
([trader.py:1243](../../local/localapp/trader.py#L1243)), 잔고도 매 호출 재조회한다
([trader.py:1100](../../local/localapp/trader.py#L1100)). 즉 **청산이 먼저 체결되어 마진이 회수된
계좌상태**를 진입 사이징이 본다. 넷팅은 청산을 체결시키지 않으므로, 순진하게 하면 진입이 회수될
마진을 못 보고 **0계약으로 사이징 → 전략 붕괴**한다(하락일 오버나이트=0).

**해결 — 넷팅될 청산이 회수할 여력을 진입 사이징에 반영한다:**

```
유효여력(S) = live_orderable(S) + Σ(같은 종목 넷팅 대상 청산 계약수)
```

같은 종목 = 같은 증거금률이므로 "N계약 청산 = N계약분 여력 회수"가 **정수로 정확히 성립**한다
(주식도 동일: N주 청산 = N주분 현금 회수, 같은 가격). 로컬 마진 수식 계산 없이 정수 덧셈만 —
모델 A의 "브로커 실값 사용" 정신을 유지한다.

**단, 넷팅되는 종목에 한해** 사이징 자금원을 "live 재조회"에서 "스냅샷 + 로컬 여력 순차 차감"으로
바꾼다(다중 진입전략이 같은 종목을 노릴 때 회수 마진 중복 계산 방지 — E2). 넷팅 없는 종목은
현행 live 재조회 그대로(현행 보존).

**한계(정직):** 브로커 마진이 비선형(상계·유지증거금 계층)이면 유효여력은 근사다. 근사가 실제보다
크면 브로커 거부가 2차 안전망(과다발주 차단), 작으면 진입이 약간 보수적. 이 근사의 실측 검증은
모의계좌 라이브 단계에서 확인한다(설계 단계 검증 불가 항목으로 명시).

## 6. 보존할 불변식 (구현 시 필수 확인)

- **무넷팅 = 현행 byte-identical** (아침 cycle 골든). `net_window` no-op 경로로 보장.
- **청산 먼저 → 진입 나중.** 잔여 발주도 청산 먼저.
- **KIS 실보유 클램프(L-04).** 넷팅은 *클램프된* 청산 수량 기준으로 상쇄.
- **킬스위치·drawdown 게이트.** 게이트로 막힌 진입은 넷팅 대상 아님 → 청산은 정상 발주.
  (넷팅은 게이트 통과한 진입 의도만 대상으로 한다.)
- **유령 진입 불가.** 이관은 기존 원장 포지션만 이동.
- **보안(§4).** 서버엔 집계(건수·절약 KRW)만. 계좌번호·원시주문 미전송.

## 7. 수수료 절약액 산정

절약 = 상쇄된 수량의 **왕복** 수수료 = `m × 계약당수수료 × 2(청산+진입)`.
계약당 수수료는 **엔진 사이징이 쓰는 동일 수수료율**에서 가져온다(별도 하드코딩 금지 —
구현 계획에서 실제 출처를 고정). 슬리피지/스프레드 절약은 추정이 부정확하므로 집계에서 제외하고
문구로만 "실제 절감은 이보다 큼(스프레드 포함)" 정도로 안내.
