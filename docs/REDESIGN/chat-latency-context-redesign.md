## 1. 구조적 뿌리

> **챗봇은 "반응형 순차 에이전트 루프 × 단일-엔티티 도구" 구조라, 표(table) 모양의 질문이 수십 개의 의존적 단일 호출로 분해되고 그 호출마다 LLM 왕복이 직렬로 누적된다. 지연 = Σ(순차 LLM 라운드), 라운드 수는 질문이 몇 조각으로 쪼개지느냐에 비례.**

3개 층 (전부 코드 근거):

1. **실행 모델 = 순차 에이전트 루프** — 한 턴 = 최대 8라운드(`agent.py:73,285`), 각 라운드가 LLM 스트리밍 호출 1회. 다음 도구는 직전 결과를 봐야 정하니 병렬 불가. 매 라운드 `messages`(히스토리+누적 결과) 전체 재전송(`agent.py:300,364`) → 뒤 라운드일수록 입력 증가.
2. **도구 = 단일 엔티티 프리미티브** — `describe`=1종목(`required:[symbol]`)·`inspect`=1종목. "N종목×M지표 비교표"를 한 번에 내는 도구 없음.
3. **의도 = 표(다중 엔티티 × 다중 지표)** — 노바렉스+피어 N개 × {PER·EV/EBITDA·PBR} × {현재·26E}. (2)에 없으니 LLM이 (1)의 루프로 손조립 → 11~21콜, 각 콜마다 라운드.

**왜 구조적:** 지연이 O(순차 LLM 라운드 수)이고 라운드 수는 질문이 쪼개지는 정도에 비례. 도구 입도(단일종목)가 질문의 모양(표)과 안 맞아 **"여러 개를 여러 기준으로 비교/집계"하는 질문은 무엇이든 느리다**(노바렉스만의 문제 아님). 섹터 오분류·8라운드 상한은 증폭기·마감처리이지 원인이 아님.

## 3. 컨텍스트 관리 — 갭과 기법

현 갭은 "통째로 되먹임"이 아니라 **선형 누적**:
1. **전 히스토리 축어 재생 → 무한 성장**(`agent.py:36-70`은 모든 메시지 재생, tool_result만 compact). → **롤링 요약**(오래된 턴 N개 요약 블록화 + 최근 K턴 축어) + 캐시 breakpoint 궁합.
2. **턴 내 compact 결과도 개수 O(도구수)** — compaction은 크기만 줄임. → **Working-memory 슬롯**(누적 상태를 구조화 표에 병합, 원시 결과 폐기).
3. **의미 기반 회수 부재**(순수 시간순). → 대화 길어질 때 retrieval 선별.

## 4. ★핵심 프레이밍

> **컨텍스트 관리는 *비용*·*일관성*을 개선하지, *지연*을 근본에서 줄이지 못한다.** 지연 지배 = 순차 LLM 라운드 *수*. 롤링 요약을 넣어도 8라운드는 여전히 8번 왕복. 지연은 아래 별개 축에서 푼다.
